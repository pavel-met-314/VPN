# Barry Cache: предложения с обязательным просмотром

## Правило

После каждой существенной задачи агент готовит краткое предложение обновления
repo-memory, но не изменяет каноническую память без явного подтверждения
пользователя. Каноническая память — только `docs/context/`.

Для роли «Архитектор» рекомендации перехода в новый чат и состав handoff
определены в [`ARCHITECT_HANDOFF.md`](ARCHITECT_HANDOFF.md). Handoff не
отменяет review-first: долговременная память обновляется только после
подтверждения пользователя.

Существенная задача — изменение архитектуры, поведения, интерфейса,
инфраструктуры, процесса проверки либо выявленный подтверждённый риск. Для
рутинного вопроса или локального косметического изменения предложение не
обязательно.

## Фаза 1: подготовить и показать

Агент завершает работу кратким блоком `Предложение Barry Cache`:

1. Проверенные факты и ссылки на исходные файлы.
2. Архитектурные решения — только если решение долговременно.
3. Выполненные команды проверки и их результат.
4. Риски, известные ограничения и незавершённые действия.
5. Предлагаемые файлы и точный diff/patch-preview.

До подтверждения запрещено:

- править `docs/context/`;
- выполнять `barry-cache finalize`, `barry-cache failure record`,
  `barry-cache feature new`, `barry-cache adr new` или любой вариант с
  `--write`;
- создавать автоматические хуки или настраивать `kb`, `cq` и shared KB;
- сохранять или читать `.env`, ключи, токены, пароли, UUID, VLESS-ссылки,
  subscription URLs и приватные адреса доступа.

Разрешены только технические, игнорируемые Git действия без семантического
обновления памяти: patch-preview в `.context-state/proposals/` и disposable-кэш,
который `resume` создаёт в `.context-cache/`.

Для технического preview агент может подготовить временный файл только в
`.context-state/proposals/` (он игнорируется Git) и показать его так:

```bash
git diff --no-index -- /dev/null .context-state/proposals/<proposal>.patch
```

Либо агент показывает эквивалентный patch в ответе. Это только предложение, не
изменение канонической памяти.

## Фаза 2: применить после одобрения

Пользователь отвечает явно, например `yes`, `одобряю` или указывает выбранный
поднабор изменений. Только после этого агент:

1. Применяет согласованный patch в `docs/context/`.
2. Показывает `git diff -- docs/context`.
3. Выполняет `barry-cache validate`.
4. Сообщает созданные/изменённые файлы.

Пользователь может ответить `no`, `отклоняю` или попросить исправить
предложение. Тогда агент не меняет каноническую память и удаляет только свой
временный preview, если он был создан.

## Использование с Codex

В начале нетривиальной задачи попросите агента выполнить:

```text
Используй Barry Cache в режиме review-first: сначала подготовь предложение
обновления контекста, покажи diff, ничего в docs/context не применяй без моего yes.
```

Чтобы получить стартовую сводку из локальной памяти:

```bash
npx --yes barry-cache@0.9.3 resume --task "<задача>"
```

После одобрения контекстного patch агент проверяет его командой:

```bash
npx --yes barry-cache@0.9.3 validate
```

`kb`/`cq` остаются выключенными. Не запускайте `kb cq login`, `kb search` или
`kb contribute`, если пользователь отдельно не разрешил внешний обмен.
